# 0.5.1 关键功能审计

## 需求验收与修订

| 需求 | 审计结果及本轮修订 |
| --- | --- |
| 包管理器更新 | 修复更新目标定位。npm/Yarn Classic 更新实际启动器所属安装目录；pip 使用所属 Python 的 `-m pip`；pnpm、Bun、uv、Composer 使用原生自更新命令。核对执行前后版本、退出码与超时，同版本不宣称已升级。 |
| 扫描后删除旧包 | 新增直接清理预览，无需先重装。默认不选包，确认后通过原管理器卸载；执行前重新核对扫描来源、安装清单、版本与目录范围，保护运行时和管理器自身，保存逐包报告。 |
| 缺失来源重装 | 读取包清单、隐藏锁文件与父目录锁文件。npm 来源未知时允许明确确认从公共仓库按同名固定版本恢复，命令固定 `https://registry.npmjs.org/`。已知 Git、URL、本地来源仍保留限制。 |
| 删除环境 | 原功能已存在；加强分类目录及 current 父目录身份检查、current 实际链接匹配与 Windows reparse point 处理。外部纳入管理的环境只移除链接，递归删除内部目录时不跟随外部链接。 |
| 扫描速度与响应 | 启动分批后台预热概览、管理器配置、系统扫描及缓存统计；复用保存的项目目录。同一读请求合并，成功结果缓存 60 秒，失败可重试，手动刷新及写操作使缓存失效。管理器查询最多并发 4 项，缓存大小统计最多并发 2 项；页面保持挂载。 |

版本声明保持 0.5.1。修改沿用现有管理器适配、任务互斥、子进程超时、元数据解析和清理报告实现。

## 本机来源缺失的原因

只读检查 `D:/DevEnvManager/envs/nodes/node-24/node_modules`：13 个顶层包的 `package.json` 都没有 `_resolved` 和 `_from`，隐藏 `.package-lock.json` 与父目录 `package-lock.json` 也不存在，包括 npm、Yarn、Codex 等包。扫描器无法从这些文件还原原始仓库。此前配置记录还显示 npm prefix 已切换至空的 `globals/npm-global`，所以只查询当前全局目录也找不到历史环境中的包。

新入口按用户确认重新下载公共包，不代表找回原来源或证明与旧文件内容相同。隔离重装不继承本机私有仓库认证；私有包不能使用此公共仓库恢复选项。

- 六套 Playwright 回归通过：包清单、旧包扫描、全局重装、pip 重装、旧包清理、迁移。覆盖直接删除确认、保护项、忙碌状态、切换页签保留、来源恢复授权与请求参数；最终修改后重跑全局重装及包清单用例通过。
- 已检查桌面与 390px 窄窗口截图，布局断言通过；读缓存测试覆盖请求合并、强制刷新、写操作失效、旧请求完成与失败重试。
- 另增启动界面回归并通过：后台扫描保持未完成时可切换页面，保存的项目目录被预热复用，概览与系统扫描不重复发起，手动重新扫描发起新请求。合计七套 UI 测试通过。
- 只读本机系统扫描测试通过，耗时 3.59 秒；该测试未传管理根目录与项目目录，仅表示此测试场景结果，不是全部启动工作的耗时或前后性能对比。
- 最终 TypeScript/Vite 生产构建通过。Windows EXE/NSIS 构建与校验结果见本文件的产物记录。

## 实际限制

- pipx、Cargo、.NET CLI 的更新取决于原安装方式或所属工具链，本版本返回具体更新途径；Corepack/Yarn Berry 等无法确认原安装位置的情况拒绝套用 npm 更新命令。
- 无解释器的孤立 Python 包目录，以及清理范围无法验证的包，不自动删除。卸载不会进入回收站。
- 全磁盘旧包扫描仍由用户手动启动；常用扫描在后台进行并不意味着启动瞬间全部完成。大目录统计、不可访问路径和慢管理器仍可能耗时，尚未量化实际机器上的提速比例。
- 概览暂不统计环境目录大小，显示未知。缓存统计仍会独立查询管理器配置，尚未做跨 IPC 的后端配置缓存。
- 未升级或删除真实用户包，未验证所有管理器的在线自更新。完整联网集成测试曾受 Maven TLS `SEC_E_NO_CREDENTIALS` 阻碍，不能将离线库测试结果视为所有下载源都已通过。
- 本轮审计及回归覆盖上述关键调用链，不构成对所有设备、安装方式和并发外部文件修改的无缺陷保证。
